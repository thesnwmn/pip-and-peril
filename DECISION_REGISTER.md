# Decision Register

A quick-reference index of every architectural and design decision for **Pip & Peril**. Read this
first; pull a detail file from `docs/decisions/` only when you need the full rationale for an area.

Maintained by the **Documenter**. Decisions are **append-and-supersede** — when a choice is
replaced, mark the old row *superseded* and link forward rather than deleting it.

## Decision log

| # | Decision | Choice | Rationale |
|---|---|---|---|
| D1 | Platform & orientation | Portrait-first web (browser), ~9:16 | Designed mobile-first; one-handed phone play suits a dice-tray UI. See `docs/concept/overview.md`. |
| D2 | Core resolution system | Coloured dice-pool; pips spent as a per-turn resource | Defining mechanic of the game; tense, expressive, expandable. See `docs/concept/overview.md`. |
| D3 | Build tooling | **SUPERSEDED by D3-v2** | Original: plain static HTML POCs + landing page. See D3-v2. |
| D3-v2 | Build tooling | Vite + TypeScript + Vitest | Zero-config dev server with HMR; type-safe modules; test harness in same environment. Introduced in feature 001. See `docs/decisions/build-tooling.md`. |
| D4 | Hosting & previews | GitHub Pages from `dist/` on `main`; PR previews to `pr-<n>/` | Zero-config static hosting; previews let the manager play-test PRs before merge. Updated in 001 to deploy from `dist/` post-build. |
| D5 | Development model | Agentic role-based harness; human manager directs, Claude takes one role per session | Lets the manager steer while Claude does the bulk of the work with a clear paper trail. See `CLAUDE.md`. |
| D6 | Numbering convention | Zero-padded sequential IDs (`001`…) shared across ideas/features; never reused | Stable references across ideas, specs, backlog, and history. |
| D7 | File naming | kebab-case for files and folders | Consistency; matches TypeScript module conventions. |
| D8 | Tile & sprite art approach | Procedural canvas drawing with `BiomePalette` abstraction (hybrid) | No external assets; fully code-driven. `drawCell` accepts a `BiomePalette`; sprites can be added later as an optional branch without changing the data model. Introduced in feature 003. |
| D9 | Canvas rendering architecture | Elastic canvas — dungeon map always present; encounter panels rise over it | Dungeon is the stage; panels are transient overlays. Map zone is a constant clip region (`MAP_Y` to `LOGICAL_H`); panels never compress it. Introduced in feature 030. See `docs/decisions/elastic-canvas.md`. |
| D10 | Encounter panel pattern | `EncounterPanel` interface + `EncounterRegistry` as the single coordinator | New encounter types plug in via `registry.register()` without touching `game.ts`. Combat is the reference implementation. Introduced in feature 034. See `docs/decisions/encounter-registry.md`. |
| D11 | Encounter transition contract | 200–350ms simultaneous panel rise + camera zoom; `ease-out` rising, `ease-in` falling | Short enough that nav input block needs no debounce message; long enough to feel cinematic. All encounter types use this contract. Introduced in feature 030. |
| D12 | Active defence model | Green pips reserved (held), not spent; 2G = full dodge; 1G = −1 damage; pure function enforces mitigation | Creates genuine opportunity cost — offence vs. survival — on every turn. Enemies must telegraph so the player has information to decide. Introduced in feature 037. See `docs/decisions/combat-mechanics.md`. |
| D13 | Combat turn structure | Roll → Allocate → Offence resolves → Tenacity window → Enemy intent fires → Defence fires → Damage → Post-damage → Intent refresh | Strict phase ordering makes item interjection windows unambiguous. Intent telegraph precedes the roll so the player allocates with full information. Introduced in feature 037; Tenacity window added in feature 046. See `docs/decisions/combat-mechanics.md`. |
| D14 | Enemy intent system | Typed `Intent.kind` discriminated union; weighted pools by tier; bosses have fixed deterministic cycles | Simple enemies teach intent types gradually; bosses are learnable puzzles. `BossSpec` encodes all boss constants (cycles, enrage threshold, title card). Introduced in feature 037; expanded in feature 046; boss pattern formalised in feature 023. See `docs/decisions/combat-mechanics.md`. |
| D15 | Enemy roster structure | 12-creature static `ENEMY_ROSTER`; tier (1/2/3) selected by `enemyTierWeights[floor][depthPhase]` lookup table; tier-1 intent set is teach-mode only | Tier determines intent complexity, not just stat values. Enemies introduced gradually across floors. Roster easily extended by adding entries. Introduced in feature 038. |
| D16 | Three-floor run structure | One-way descent (Floor 1 → 2 → 3 → boss); stairwell tile unlocked at per-floor threshold; boss room is only exit on floor 3 | Fixed arc creates a learnable structure across runs. One-way descent enforces commitment. Boss gate gives floor 3 a clear objective. Introduced in feature 022. |
| D17 | Dungeon tuning module | All dungeon pacing constants in `src/dungeon/tuning.ts`; no magic numbers elsewhere | Single source of truth for all offer weights, phase thresholds, shop debt, trap difficulty, enemy tier weights. Introduced in feature 022. |
| D18 | Room offer weight system | Base weights lookup by `(floor, depthPhase)`; three runtime overrides (Stairwell threshold, Shop debt, Boss distance factor); normalized before deal | Depth-and-floor weighting creates natural pacing without scripted sequences. Shop debt guarantees exactly one shop per floor. Boss distance factor means the boss lurks far from where Pip arrived. Introduced in feature 022. |
| D19 | Item interjection windows | Eight defined windows (`pre-roll`, `on-roll-luck`, `during-allocation`, `on-strike`, `post-spend-tenacity`, `on-enemy-hit`, `post-damage`, `between-turns`); every item assigned exactly one | Unambiguous timing prevents two items competing for the same moment. Window assignment is the Designer's first question when speccing a new item. Formalised in feature 048. See `docs/decisions/item-interjection.md`. |
| D20 | Luck interrupt pattern | Amber overlay fires at "check failed, before consequence" (non-combat) and `on-roll-luck` window (combat); 3s auto-dismiss; greyed after pips spent this turn | Luck items create a dramatic "save" moment without blocking the outcome — the player chooses whether to use it. Introduced in feature 048. See `docs/decisions/item-interjection.md`. |
| D21 | Item charges vs. quantity | Stackable consumables use `quantity: number`; limited-use items use `charges: number`; `consumeItem()` handles charge decrement and removal | Prevents confusing "how many uses left?" for items that deplete differently from single-use consumables. Introduced in feature 048. |
| D22 | MetaState persistence | Versioned `localStorage` key `pip-meta-v1`; graceful fallback to in-memory defaults if storage unavailable; backward-compatible migrations per version bump | Single, typed cross-run store. Version field allows schema evolution without breaking existing saves. Introduced in feature 029; `runCount` added in feature 053. |
| D23 | Dynamic pool composition | Run pool = `MetaState.permanentPool` + `activeWeapon.addedDice`; never hardcoded | Weapons and meta upgrades compose cleanly. New weapon types or upgrade paths require no change to the roll engine. Introduced in feature 029. |
| D24 | Weapon system model | Four static weapon specs in `src/meta/weapons.ts`; mandatory selection before each run; live pool preview in selection panel | Weapon choice is the run's defining character before the first room. Static specs ensure determinism; the selector shows the player exactly what they are committing to. Introduced in feature 029. |
| D25 | Unified run summary routing | Both victory and defeat end at the full-screen Run Summary screen before returning to camp; no "defeat → main menu" short-circuit | Same screen for both outcomes normalises the debrief and reinforces the roguelike loop. Camp is the hub between all runs. Introduced in feature 024 (screen) + feature 029 (camp). |
| D26 | Camp screen layout | Fixed scene zone (≥55% height) / activity bar (≤45%) split with non-moving 1px divider; all navigation through activity bar buttons; scene zone non-interactive | Thumbable navigation in the bottom zone; ambient scene above. Removing tap targets from the scene eliminated ambiguous hit regions. Introduced in feature 029; redesigned into stable form in feature 090. |
| D27 | Sub-panel dismiss contract | Camp sub-panels: ✕ button (44×44px, top-right), 400ms ease-out rise, 300ms ease-in fall, scrim dims scene to 40% while open; lightweight read-only panels (notices): tap-outside to dismiss | Explicit ✕ for panels with actions (prevents accidental dismissal); tap-outside for read-only info (low friction). Established in feature 090. |
| D28 | Greyed-never-hidden affordance | Unaffordable actions render greyed with cost legible; never hidden | Teaches what becomes possible as the player builds a pool. Hidden buttons imply the action does not exist; greyed implies "not yet". Established in feature 037; applied throughout combat and camp. |
| D29 | Constants in dedicated data modules | Dungeon pacing: `DUNGEON_TUNING`; enemy specs: `ENEMY_ROSTER`; boss data: `BossSpec` in `src/combat/boss-panel.ts`; weapon specs: `src/meta/weapons.ts` | Magic numbers in logic are a maintenance hazard. Centralised modules make rebalancing a data change, not a code change. Applied across features 022, 023, 038, 029. |
| D30 | Unified check panel | Reusable `CheckPanel` module in `src/encounter/check-panel.ts`; four-band result model (critical/success/partial/failure); used by NPC encounters and any future non-combat dice check | Single resolution UI for all non-combat checks ensures consistent feel and teaching. Four bands (not pass/fail) create fail-forward narrative outcomes. Introduced in feature 028. |
| D31 | NPC dialogue model | `NpcScript` with `NpcNode` tree; responses optionally gate on `CheckSpec`; outcomes route to next nodes or terminal rewards | Text-first encounter (inverse of combat). Check appears *inside* dialogue when a response triggers it, not as a separate mode. Three founding archetypes establish the pattern for future NPCs. Introduced in feature 028. |
| D32 | Notice board generation | Template banks seeded by `MetaState.runCount`; two notices always from different categories; ephemeral — not persisted, regenerated each session | Cheap world-voice without content authoring per run. `atmosphericLine` (first notice text) exposed as a named field for future run-start transitions. Introduced in feature 053. |
