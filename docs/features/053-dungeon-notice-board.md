# 053 · Dungeon Notice Board

**Status:** READY
**Source idea:** Backlog item 053 (originated in `docs/concept/meta-progression.md`)
**Depends on:** 029 (camp hub, MetaState)

---

## Summary

The dungeon notice board is a small physical object in Pip's camp — rough wood, scraps of
paper pinned to it — that presents two generated notices before each run. Tapping it reveals
the notices as warm, handwritten-style cards. The notices are assembled from template banks
across four categories (enemy activity, merchant sightings, atmosphere, past-run echoes) and
seeded with a small amount of actual game state so they feel rooted in Pip's history rather
than purely random. They prime the feel of the upcoming descent and make successive runs feel
distinct before the first tile is placed. Notices are never guarantees — the merchant spotted
heading down may or may not still be there — but they shift what kind of run the player
*expects*. The notices do not mechanically alter run generation; that wiring is deferred.

## Acceptance criteria

### MetaState extension

1. `MetaState` is extended with a `runCount: number` field (default `0`). It is incremented by 1
   each time a run ends (boss victory or Pip's death) at the same point scraps are transferred
   (criterion 6 of feature 029). This field persists across sessions.

2. Existing saved `MetaState` without a `runCount` field is treated as `runCount: 0` on load
   (backward-compatible migration, no version bump required).

### Notice generation

3. When the camp screen initialises (on page load or after run-end return), exactly **two
   notices** are generated and held in ephemeral run-start state. They are not persisted to
   `localStorage` — if the page reloads at camp, they are regenerated.

4. Each notice is generated by: (a) selecting a notice category from the eligible pool;
   (b) selecting one template string from that category's bank; (c) filling any `{variable}`
   slots with values resolved from the current game state.

5. The two notices are **never from the same category**.

6. The eligible category pool is:
   - Always included: `enemy-activity`, `merchant-sighting`, `atmosphere`
   - Included only when `MetaState.runCount > 0`: `past-run-echo`

7. Category selection is uniformly random from the eligible pool. No weighting is required in
   this version.

8. If a template string contains no `{variable}` slots, it is used as-is. If it contains
   `{variable}` slots, all slots must be filled before the notice is stored; a notice string
   with an unfilled slot must not be displayed.

### Notice board in the camp

9. The camp renders a notice board object in the lower-left area (as shown in the wireframe
   below) — a dark wooden board with two visible paper rectangles pinned to it. The paper backs
   are visible; the text is not readable inline.

10. Tapping the notice board opens a **lightweight notice panel** that rises from the bottom.
    This is not a full sub-screen: it has no "Done" or confirmation button. Tapping anywhere
    outside the panel closes it.

11. The panel displays both notices as card objects — warm paper background, hand-inked text
    treatment — stacked vertically with a small gap between them.

12. The panel rises with a cool-temperature transition (~400 ms). Dismissal sinks the panel back
    in ~300 ms.

### Notice content

13. The generated notice text uses the tone established in the template examples in the Design
    detail section below. The Engineer may expand the template bank; the examples are a minimum
    baseline, not an exhaustive list.

14. Each template string (after variable resolution) fits on **two lines or fewer** at the
    notice card's display width. Templates must be written with this constraint in mind.

### Atmospheric line hook

15. The generated notice state exposes an `atmosphericLine` property: the full text of the first
    generated notice (index 0). This is a named field on the ephemeral state object so a future
    run-start transition spec can read it without parsing the display structure. It is not
    rendered anywhere in this feature beyond the notice panel.

## Scope / non-goals

- **Challenge notices** (self-imposed run challenges, e.g. "a hunter bet you…"): deferred.
  Challenge notices imply external tracking of run outcomes, which is the Marks of Descent
  system (052). Seeding the player's mindset with a run challenge belongs there.
- **Mechanical wiring**: notices do not affect run generation parameters. Enemy-activity notices
  do not alter enemy weighting; merchant-sighting notices do not affect shop placement. This
  wiring is an incremental follow-on, not part of this feature.
- **Notice history log**: past notices are not stored or viewable. They are ephemeral.
- **Pin/paper animation** at notice generation: no visual flourish when notices are pinned —
  they are simply present when the board is tapped.
- **Inline readable text in the camp view**: notice text requires a tap to read. The board
  object shows paper backs only.
- **Run-start floor title card**: the atmospheric line field is exposed but not consumed here.
  The title card / run-start transition sequence is a future spec.

## Design detail

### MetaState extension

`MetaState` (version 1 as defined in feature 029) gains one field:

```
MetaState (version 1, amended by 053)
└── runCount: number   ← default 0; increments at run-end before scraps transfer
```

The increment happens in the same transaction as the scraps transfer: `runCount += 1` before
`scraps += RunState.gold`. Order within the transaction does not matter.

### Ephemeral notice state

The two notices are held in a plain object (not persisted):

```
NoticeState
├── notices: [NoticeEntry, NoticeEntry]   ← exactly two
└── atmosphericLine: string              ← notices[0].text, for run-start transition use

NoticeEntry
├── category: 'enemy-activity' | 'merchant-sighting' | 'atmosphere' | 'past-run-echo'
└── text: string                          ← fully resolved (no remaining {variable} slots)
```

`NoticeState` is regenerated each time the camp screen initialises. It lives in component or
module state — no need for a dedicated state layer beyond what already owns camp state.

### Template variables

The following variables are resolved at generation time:

| Variable | Source | Example values |
|---|---|---|
| `{run_count}` | `MetaState.runCount` | `3`, `12` |
| `{run_count_ordinal}` | derived from `runCount` | `"third"`, `"twelfth"` |
| `{comparative}` | random pick from list | `"louder"`, `"quieter"`, `"stranger"`, `"faster"`, `"colder"` |

The `{run_count_ordinal}` derivation should handle 1–20 named ordinals (`"first"` through
`"twentieth"`) and fall back to `"{n}th"` for higher values.

No further variables are introduced in v1. Future mechanical wiring will add variables drawn
from run generation (enemy type, shop density, boss type) without restructuring this system.

### Template banks

These are the minimum starting templates. The Engineer should add to the banks freely; the
examples below define the tone, not the ceiling.

**Enemy activity** (always eligible):

- `"Rustling in the lower corridors. Bring something sharp."`
- `"The scratching on the walls has been {comparative} than usual."`
- `"Three travellers went in yesterday. One came back, and wouldn't say what they saw."`
- `"No sign of the patrol they sent to the lower levels."`

**Merchant sighting** (always eligible):

- `"A heavyset badger was seen descending with a full pack. Looking to sell, by the look of him."`
- `"Word is there's a tinker camped near the second landing. If he's still there."`
- `"Smells of pine pitch and dried herbs on the upper stairs. Someone passed through recently."`
- `"A price list pinned near the first doorway. Hand-drawn. Mostly legible."`

**Atmosphere** (always eligible):

- `"The deep smells wrong tonight."`
- `"The torches are burning {comparative} than yesterday. No one's touched them."`
- `"Cold air from below, even though the season is warm."`
- `"Something shifted in the night. Can't say what."`
- `"Descent {run_count_ordinal}. The dungeon doesn't look different from here, but it feels it."`

**Past-run echo** (eligible when `runCount > 0` only):

- `"Someone left marks on the wall near the entrance. Fresh scratches. A tally of some kind."`
- `"The stairs still smell of the last descent. Or maybe that's just how it always is."`
- `"Heard something moving down there last night. Rhythmic. Deliberate."`
- `"Run {run_count}. Still standing. The dungeon must be slipping."`

### Generation flow

```
camp screen initialises
│
├─ build eligible pool:
│    if runCount === 0 → [enemy-activity, merchant-sighting, atmosphere]
│    else              → [enemy-activity, merchant-sighting, atmosphere, past-run-echo]
│
├─ pick category A at random from pool
├─ pick category B at random from pool, excluding A
│
├─ pick template string from category A's bank (uniform random)
├─ pick template string from category B's bank (uniform random)
│
├─ resolve {variable} slots in each string
│
└─ store as NoticeState = {
     notices: [
       { category: A, text: resolvedA },
       { category: B, text: resolvedB }
     ],
     atmosphericLine: resolvedA
   }
```

If a template bank has only one entry (unlikely but possible after launch), that template is
always selected for its category. No error; just low variety until more templates are added.

### Camp screen integration

The notice board object is added to the camp canvas in the lower-left area (replacing or
fleshing out whatever stub 029 renders at that position). It is always a tap target —
tapping opens the notice panel even on the very first visit (where notices will be from
the three-category pool, without past-run echoes).

The notice board's visual state does not change between "notices available" and "notices
not yet read" — there is no unread indicator. The board is a passive environmental object,
not a notification.

### Panel behaviour

- Rises from screen bottom, consistent with all other camp panels.
- Cool temperature: parchment surface (warm, not dungeon-dark).
- No header label needed — the two notice cards are self-evident.
- No "Done" or "OK" button. Tapping anywhere outside the panel bounds closes it.
- A faint ghost label ("tap to dismiss") may appear at the bottom of the panel and fade
  after 2 seconds. This is optional — include it only if tap-to-dismiss is not obvious
  from user testing.

### Edge cases

- **First ever load (runCount = 0):** Three-category pool (no echoes). Two notices
  selected normally from the three eligible categories.
- **Variable resolution failure:** If `runCount` is unexpectedly undefined or NaN, treat
  it as 0. Templates with `{run_count}` or `{run_count_ordinal}` should fall back to a
  generic value (`"this"` for ordinals, `"0"` for count) rather than rendering `{variable}`
  literally. A console warning is appropriate.
- **Same template string selected twice (different categories):** Possible but unlikely.
  No constraint required — if both generated notices happen to convey similar tone, that
  is acceptable.

### Colour tokens

| Token | Value | Used for |
|---|---|---|
| `--notice-bg` | `#f5e8c4` | Notice card paper background |
| `--notice-text` | `#1a0f05` | Notice card ink text |

Pin accent reuses `--gold` (`#c8941e`) — no new value needed.

The notice panel surface (behind the cards) uses `--camp-surface` from feature 029 — warm
brown, consistent with the camp's parchment temperature. No new panel surface token needed.

### Typography / sizing

| Element | Size | Style | Colour |
|---|---|---|---|
| Notice card text | 13px | italic, regular weight | `--notice-text` |
| Notice card body | 12px leading | — | — |

Italic weight on the notice text suggests a handwritten/inked quality without requiring a
second typeface. If the project's font does not have a distinct italic variant, a slight
colour differentiation (`--notice-text` on `--notice-bg`) alone is sufficient to distinguish
the notice cards from the rest of the camp UI.

## Open questions

None blocking. The feature is `READY` as specified.

**Tuning notes** (for the Engineer and future Designer):

- **Template bank growth:** The initial banks are thin (4–5 entries each). A content pass to
  add 5–10 templates per category would significantly reduce repetition for players with more
  than ~10 runs. This is low-effort and can happen without a new spec — it is a code change,
  not a design decision.
- **Challenge notices:** Deferred to feature 052. When speccing 052, consider whether challenge
  notices are seeded from the board (player reads the challenge before descending) or triggered
  in-run (NPC offers the challenge mid-descent). The former is a notice-board extension; the
  latter is its own flow.
- **Mechanical wiring:** When enemy weighting, shop density, or boss type become available from
  run generation, the template variable list expands to include them. No structural change to
  this feature required — just new variables and new templates that use them.
